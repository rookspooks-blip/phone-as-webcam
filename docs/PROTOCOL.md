# Протокол Lensbridge — `lbp/1.0` (черновик)

> Статус: черновик на согласование вместе с [`ARCHITECTURE.md`](ARCHITECTURE.md). Протокол собственный, не совместим с DroidCam/Iriun и не основан на них.
> Ключевые слова НУЖНО / СЛЕДУЕТ / МОЖНО — в смысле RFC 2119 (MUST / SHOULD / MAY).

## 1. Роли и термины

- **Сервер** — телефон (Android-/iOS-приложение). Снимает и кодирует медиа, слушает порты.
- **Клиент** — ПК (десктоп-приложение, CLI, OBS-плагин) или браузер для `/video`.
- **Часы сервера** — монотонные часы телефона в микросекундах (`u64`), общая база для всех потоков. Сервер обязан привести метки камеры и микрофона к этой базе (на Android — учитывать `SENSOR_INFO_TIMESTAMP_SOURCE` и `AudioRecord.getTimestamp()`).
- **pts** — момент захвата (не отправки) в часах сервера, мкс.

## 2. Версионирование

- Строка версии: `lbp/<major>.<minor>`, сейчас `lbp/1.0`.
- **major** меняется при несовместимых изменениях. Клиент и сервер с разными major НЕ ДОЛЖНЫ продолжать сессию (ошибка `proto_unsupported`, WS close `4001`).
- **minor** добавляет возможности; конкретные возможности объявляются флагами в `caps.features` (например `"h264"`, `"opus"`, `"udp_rtp"`), а не выводятся из номера.
- Неизвестные поля JSON НУЖНО игнорировать; неизвестные типы сообщений — отвечать `error{code:"unknown_type"}` и продолжать.

## 3. Транспорты и порты

| Порт | Протокол | Когда | Аутентификация |
|---|---|---|---|
| 4747/tcp | HTTP/1.1 + WebSocket, plain | Браузер, USB-туннели, Wi-Fi без пейринга (если разрешено пользователем) | Фильтр источника: только loopback/RFC 1918/link-local/ULA. Опционально `?token=` |
| 4748/tcp | HTTPS + WSS, TLS 1.3 | Wi-Fi после пейринга (по умолчанию) | mTLS: оба отпечатка закреплены при пейринге (§8) |
| 4749/tcp (на ПК) | HTTPS + WSS | PWA-режим | Одноразовый токен из QR |

USB: Android — `adb forward tcp:<L> tcp:4747` (клиент подключается к `127.0.0.1:<L>`); iOS — usbmux `Connect` на порт устройства 4747. Поверх USB шифрование НЕ требуется (канал физический), но МОЖЕТ использоваться 4748.

Обнаружение: mDNS/DNS-SD `_lensbridge._tcp.local`, порт 4747, TXT: `v=1`, `id=<первые 16 hex SHA-256 сертификата сервера>`, `name=<имя устройства>`, `tls=4748` (если включён), `pair=1` (если есть хоть один сопряжённый клиент).

## 4. HTTP-эндпоинты (оба порта)

### `GET /info`
```json
{
  "proto": "lbp/1.0",
  "app": "lensbridge-android",
  "app_version": "0.1.0",
  "device": { "name": "Pixel 7", "platform": "android", "os_version": "14", "id": "3f2a…" },
  "features": ["mjpeg", "opus", "pcm_s16le", "control", "h264"],
  "auth": { "plain_allowed": true, "token_required": false, "tls_port": 4748 }
}
```

### `GET /video`
Параметры (все необязательные, иначе текущие настройки): `camera`, `w`, `h`, `fps`, `q` (1–100), `token`.

Ответ:
```
HTTP/1.1 200 OK
Content-Type: multipart/x-mixed-replace; boundary=lbframe
Cache-Control: no-store
Connection: close

--lbframe
Content-Type: image/jpeg
Content-Length: 48211
X-LB-Seq: 1024
X-LB-PTS: 812345678901
X-LB-Orientation: 0

<JPEG>
--lbframe
…
```

- `X-LB-Seq` — `u32`, растёт на 1 на каждый **закодированный** кадр (пропуски = кадры, сброшенные сервером для этого получателя).
- `X-LB-PTS` — pts кадра.
- `X-LB-Orientation` — 0/90/180/270: на сколько повернуть кадр по часовой для «правильной» ориентации. Сервер ПО УМОЛЧАНИЮ поворачивает сам и шлёт 0; ненулевое значение — если пользователь включил «не поворачивать на телефоне» (экономия CPU).
- Медленный получатель: сервер держит на соединение очередь ≤ 2 кадров, лишние сбрасывает (сохраняя самый свежий).
- Браузеры игнорируют заголовки `X-LB-*` и показывают поток как обычный MJPEG.
- Одновременно: до 4 получателей `/video`.

### `GET /snapshot.jpg`
Один кадр, те же заголовки `X-LB-*`.

### `GET /ws/control` — WebSocket, текстовые JSON-сообщения (§6).
### `GET /ws/media?streams=audio[,video]` — WebSocket, бинарные кадры (§5).

Одновременно активна **одна** управляющая сессия. Новый клиент с `hello{"takeover":true}` вытесняет старого (тот получает `bye{reason:"taken_over"}`), без — получает `error{code:"busy"}`.

## 5. Бинарные медиакадры (`/ws/media`)

Одно WebSocket-сообщение = один кадр (аудиофрейм или access unit H.264). Порядок байт — big-endian.

```
 0      1      2      3      4                8                               16
+------+------+------+------+----------------+-------------------------------+---------
| ver  | type |codec |flags |   seq (u32)    |          pts_us (u64)         | payload…
+------+------+------+------+----------------+-------------------------------+---------
```

| Поле | Значения |
|---|---|
| `ver` | `1` |
| `type` | `1` = video, `2` = audio |
| `codec` | `1` = MJPEG, `2` = H.264 (Annex B), `3` = H.265 (резерв), `16` = Opus, `17` = PCM s16le |
| `flags` | bit0 `KEY` (IDR / независимый кадр), bit1 `CONFIG` (SPS/PPS или OpusHead), bit2 `DISCONT` (разрыв: смена настроек, восстановление после прерывания), bit3 `END_OF_STREAM` |
| `seq` | отдельный счётчик для каждого `type` |
| `pts_us` | pts первой выборки |

Аудио:
- Opus: 48 кГц, моно (стерео — если устройство и настройка позволяют), фреймы 10 или 20 мс (по умолчанию 20 мс; в режиме «минимальная задержка» — 10 мс), битрейт 32–128 кбит/с (по умолчанию 64).
- PCM s16le: 48 кГц, моно, 10 мс (480 выборок = 960 байт). Параметры объявляются в `stream_config`.
- Перед первым кадром и после каждого изменения сервер шлёт в `/ws/control` сообщение `stream_config` (§6.6).

H.264 (фаза 2):
- Annex B, baseline/constrained-high без B-кадров, `CONFIG`-кадр с SPS/PPS перед каждым IDR. GOP по умолчанию 2 с; по `request_keyframe` IDR выдаётся ≤ 1 кадра.
- Отправитель держит очередь ≤ ~150 мс; при переполнении сбрасывает всё до следующего IDR, ставит `DISCONT` и сам запрашивает у кодера IDR; снижает битрейт (AIMD) и сообщает в `stats`.

## 6. Управляющие сообщения (`/ws/control`)

Общий вид: `{"t": "<тип>", "id": <u32, необязателен>, …}`. Запросы с `id` получают ответ `ack`/`error` с тем же `id`.

### 6.1 Handshake

Клиент → сервер (первое сообщение, таймаут 5 с):
```json
{"t":"hello","proto":"lbp/1.0","client":"lensbridge-desktop","client_version":"0.1.0",
 "os":"linux","token":"<опц., из URL/пейринга>","takeover":false}
```
Сервер → клиент:
```json
{"t":"welcome","proto":"lbp/1.0","session":"6f1c…","server_time_us":812345000000,
 "features":["mjpeg","opus","h264"],"active":{ …текущие параметры, как в set… }}
```
Ошибки: `proto_unsupported` (close 4001), `unauthorized` (4003), `busy` (4009).

### 6.2 Возможности устройства
`{"t":"get_caps","id":1}` →
```json
{"t":"caps","id":1,"cameras":[
  {"id":"0","facing":"back","label":"Основная","sensor_orientation":90,
   "formats":[{"w":3840,"h":2160,"fps":[30]},{"w":1920,"h":1080,"fps":[30,60]},{"w":1280,"h":720,"fps":[30,60,120]}],
   "codecs":["mjpeg","h264"],
   "zoom":{"min":1.0,"max":8.0},"torch":true,
   "focus":{"modes":["continuous","auto","manual"],"min_distance":10.0},
   "exposure":{"comp_min":-12,"comp_max":12,"comp_step":0.1667,"manual_iso":[50,3200],"manual_shutter_ns":[100000,250000000]},
   "stabilization":["off","on"]}],
 "audio":{"codecs":["opus","pcm_s16le"],"rates":[48000],"channels":[1,2],"sources":["mic","camcorder","voice_recognition"]}}
```
Списки форматов/FPS строятся **динамически** из `StreamConfigurationMap`/`AVCaptureDevice.formats`; ничего не захардкожено.

### 6.3 Изменение параметров
```json
{"t":"set","id":7,"params":{
  "camera":"0","w":1280,"h":720,"fps":30,"codec":"mjpeg","quality":80,"bitrate":6000000,
  "zoom":1.5,"torch":false,"mirror":false,
  "focus":{"mode":"tap","x":0.5,"y":0.4},
  "exposure":{"comp":0.0,"lock":false},
  "audio":{"enabled":true,"codec":"opus","bitrate":64000,"channels":1,"source":"mic"},
  "screen":"dim"}}
```
Все поля необязательны. Ответ: `{"t":"ack","id":7,"applied":{…фактически применённое…}}`. Сервер МОЖЕТ подобрать ближайшее поддерживаемое значение — в `applied` всегда фактическое. Смена разрешения/камеры/кодека вызывает `DISCONT` в потоках. `mirror` — только метаданные для клиента (зеркалирование выполняет клиент, чтобы превью и выход могли различаться). `screen`: `on` | `dim` | `off` (`off` только Android).

### 6.4 Синхронизация часов
Клиент раз в 1 с (первые 5 с — раз в 200 мс):
```json
{"t":"ping","id":42,"c0":1700000000123456}
```
Сервер отвечает немедленно:
```json
{"t":"pong","id":42,"c0":1700000000123456,"s1":812345678901}
```
Клиент по моменту приёма `c2`: `rtt = c2 − c0`, `offset = s1 − (c0 + c2)/2`. Используется оценка из окна 30 с с минимальным `rtt`; дрейф — линейная регрессия по окну. Цель точности: ±2 мс по USB, ±5 мс по Wi-Fi.

### 6.5 Прочие запросы
- `{"t":"request_keyframe"}` — немедленный IDR (H.264).
- `{"t":"bye","reason":"user"}` — корректное завершение; сервер останавливает захват, если нет других получателей.

### 6.6 Сообщения сервера
- `stream_config`: `{"t":"stream_config","stream":"audio","codec":"opus","rate":48000,"channels":1,"frame_us":20000}` / для видео — `w`, `h`, `fps`, `codec`, `profile`.
- `stats` (раз в 1 с): `{"t":"stats","fps_cap":30.0,"fps_enc":29.9,"enc_ms":7.2,"tx_kbps":18400,"dropped":3,"queue_ms":12,"battery":81,"charging":true,"temp_c":38.5,"thermal":"none"}`.
- `event`: `{"t":"event","kind":"<…>","detail":{…}}`, kind: `camera_interrupted` (звонок/другое приложение/фон iOS), `camera_resumed`, `audio_interrupted`, `audio_resumed`, `orientation` (`{"deg":90}`), `thermal_throttle`, `low_battery`, `network_changed`.
- `error`: `{"t":"error","id":7,"code":"unsupported_value","message":"…"}`. Коды: `proto_unsupported`, `unauthorized`, `busy`, `unknown_type`, `bad_request`, `unsupported_value`, `camera_unavailable`, `internal`.

## 7. Тайминги и поведение при сбоях

| Параметр | Значение |
|---|---|
| WebSocket ping (уровень WS) | каждые 2 с; нет ответа 6 с → соединение мёртвое |
| Таймаут `hello` | 5 с |
| Переподключение клиента | экспоненциально 0,5 → 1 → 2 → 4 → 8 с (максимум), сброс после 10 с стабильной работы |
| Восстановление камеры на сервере | после `camera_interrupted` — повтор открытия каждые 1 с до успеха; затем `DISCONT` + `camera_resumed` |
| Jitter buffer клиента | адаптивный, цель = p95 джиттера + 5 мс, пределы 10–120 мс (Wi-Fi), 5–40 мс (USB) |
| A/V-синхронизация | аудио — мастер; видеокадр, опоздавший > 1 интервала кадра, сбрасывается; ранний — ждёт; дрейф аудио компенсируется ресемплингом в пределах ±0,5 % |

## 8. Безопасность и пейринг

### 8.1 Идентичность
При первом запуске каждая сторона генерирует пару ключей ECDSA P-256 и самоподписанный сертификат (срок 20 лет). Идентификатор = SHA-256 от DER-сертификата. Закрытый ключ: Android Keystore, iOS Keychain, ПК — системное хранилище (Windows DPAPI, macOS Keychain, Linux Secret Service или файл с правами 0600).

### 8.2 QR-пейринг (основной)
1. Пользователь жмёт на ПК «Сопрячь телефон». ПК открывает **окно пейринга** на эфемерном TCP-порту на 120 с и генерирует одноразовый токен (128 бит, CSPRNG).
2. ПК показывает QR:
   ```
   lensbridge://pair?v=1&h=192.168.1.10,fd00::12&p=47123&t=<base32 токен>&f=<base64url SHA-256 серт. ПК>&n=<имя ПК>
   ```
3. Телефон сканирует QR, подключается по TLS 1.3 к `h:p` и **проверяет, что отпечаток сертификата ПК равен `f`** (иначе — обрыв и предупреждение о возможной атаке).
4. Телефон отправляет `POST /pair` `{"token":"…","phone_cert_fpr":"…","phone_name":"…","tls_port":4748}`. Его собственный сертификат также предъявляется как клиентский в этом TLS-соединении, и ПК проверяет совпадение с `phone_cert_fpr`.
5. ПК сравнивает токен за постоянное время, токен немедленно аннулируется (одна попытка; при неверном — окно закрывается). Сохраняет отпечаток телефона. Ответ `{"ok":true}`.
6. Телефон сохраняет отпечаток ПК в список разрешённых клиентов.
7. Дальше ПК подключается к телефону на **4748 с клиентским сертификатом**: телефон пускает только клиентов из списка, ПК проверяет отпечаток телефона. Сертификаты самоподписанные — проверка цепочки не делается, только закрепление отпечатка.

### 8.3 Пейринг по коду (запасной, без входящих подключений на ПК)
Телефон показывает 8-символьный код. ПК подключается к телефону на 4748 (TLS без проверки отпечатка), обе стороны выполняют SPAKE2 с кодом и подтверждают через MAC свои отпечатки сертификатов, видимые в TLS-сессии. После успеха — как шаги 6–7. Ошибка кода → блокировка на 30 с, после 5 ошибок — новый код.

### 8.4 Политика по умолчанию
- 4747 (plain) — включён, но принимает только loopback/приватные адреса; в настройках можно выключить plain для Wi-Fi полностью (тогда только USB и 4748).
- Сервер не слушает публичные адреса и не использует UPnP.
- Отзыв: в приложениях на обеих сторонах список сопряжённых устройств с удалением.
- Ни облака, ни телеметрии, ни внешних запросов.

## 9. Расширения (зарезервировано)

- `udp_rtp` — RTP/UDP для видео по Wi-Fi, если замеры покажут, что TCP не укладывается в бюджет задержки. Согласуется через `set{"transport":"rtp","rtp_port":…}`; SRTP с ключами, выведенными из TLS-сессии (exporter, RFC 5705).
- `h265` — по мере появления поддержки декодеров на ПК.
- `ptz`/`roi` — область интереса для экспозиции.

## 10. PWA-режим (браузер → ПК)

Отличается направлением: **ПК — сервер**, браузер телефона — источник.
1. ПК поднимает HTTPS на 4749 (самоподписанный сертификат ПК) и показывает QR `https://<ip>:4749/#t=<токен>`.
2. Пользователь принимает предупреждение о сертификате (или заранее устанавливает CA-профиль ПК).
3. Страница вызывает `getUserMedia`, открывает WSS `/signal` с токеном, обменивается SDP с ПК (`webrtc-rs`). Кандидаты — только host (без STUN/TURN). Видео H.264 или VP8, аудио Opus.
4. Страница держит экран включённым (Screen Wake Lock API; для Safari < 16.4 — обход через зацикленное невидимое видео) и предупреждает, что сворачивание браузера останавливает камеру.
5. Управление (камера, разрешение, зум/вспышка, где поддерживается `MediaTrackCapabilities`) — через тот же WSS в формате сообщений §6.
